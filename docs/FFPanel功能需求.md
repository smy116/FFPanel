# FFPanel 功能需求

### 1. Docker 部署与 WebUI

项目运行于 RK3588 设备，使用 Docker 部署，镜像中包含应用本身、rclone 以及编译后的 ffmpeg-rockchip[https://github.com/nyanmisaka/ffmpeg-rockchip]，不依赖宿主机安装 FFmpeg。

提供适合桌面浏览器使用的 WebUI，整体采用简洁、明亮主题。前端建议使用 Vue 3 + TypeScript + Vite，并选用成熟的组件库实现表单、步骤向导、进度条、任务列表、弹窗等界面。

Docker 应支持映射 RK3588 硬件编解码所需设备，并通过 volume 挂载配置、缓存、本地媒体目录等数据，例如：

- `/config`：应用及 rclone 配置；
- `/cache`：远程文件缓存、转码临时文件；
- `/media`：可选的宿主机本地媒体目录。

应用数据、任务记录等需要持久化，容器重启后不能丢失任务历史。第一版统一使用位于 `/config` 持久卷中的本地数据库（建议 SQLite，例如 `/config/ffpanel.db`）保存任务、文件状态、参数决策、错误与重试信息；`/cache` 只保存可清理的下载缓存与临时输出，不作为任务状态的唯一来源。

应用启动时必须执行任务恢复扫描：识别上一次进程退出时仍处于运行阶段的任务/文件，将其转换为可解释的“已中断”状态，并允许用户通过 Retry 继续处理未完成文件。

---

### 2. rclone 远程存储支持

使用 rclone 支持 SFTP、SMB、WebDAV、S3、OneDrive、Google Drive 等 rclone 已支持的远程存储协议。

rclone 配置由用户预先在宿主机完成，并通过 Docker 挂载已有的 `rclone.conf` 到容器。项目本身不提供 remote 的创建、修改、OAuth 登录、密码管理等配置功能。

默认配置路径建议为：

`/config/rclone/rclone.conf`

同时允许通过环境变量覆盖配置文件路径。

应用通过 `rclone listremotes` 自动读取用户已经配置好的 remote，并在创建任务时提供选择。

远程目录浏览通过 rclone 获取目录及文件信息，前端不需要感知 remote 实际使用的是 SFTP、SMB、WebDAV 还是其他协议。

未配置 rclone 或配置文件不可用时，只禁用远程存储功能，不影响本地文件转码。

远程输入文件默认采用本地缓存模式：

`远程文件 → rclone 下载到缓存 → ffprobe → ffmpeg 转码 → rclone 上传输出`

不使用 `rclone cat | ffmpeg` 或类似管道作为主要处理方案。

### 3. 页面及整体信息架构

WebUI 至少包含两个主要页面：

**创建新任务**

用于建立一次批量转码任务，通过步骤向导完成输入目录、输出目录及编码参数设置。

**任务清单**

展示已经创建的任务，包括等待、运行中、已完成、失败、已停止等状态。

一个用户创建的批量转码操作对应一个任务，而不是每一个视频文件对应一个任务。

任务内部可以维护多个文件的独立处理状态，但 WebUI 顶层任务列表仍然只显示一条任务。

### 4. 创建新任务向导

创建任务采用分步骤向导，至少包含以下步骤。

#### 第一步：路径与来源

输入来源支持：

- 本地目录；
- rclone remote。

选择 rclone remote 后，可以逐级浏览其目录。

扫描输入目录后识别支持的视频文件，可以递归扫描子目录，并保存文件相对于输入目录的路径，以便输出时保留原有目录结构。

输出位置同样支持：

- 本地目录；
- rclone remote。

应允许输入和输出使用不同的存储，例如：

`SFTP → 本地`

`本地 → WebDAV`

`S3 → SMB`

`remote A → remote B`

输出文件应避免覆盖正在生成的文件，可以先生成临时文件，成功后再变为最终文件名。

**伴随文件复制策略**

创建任务时提供一个互斥的三档选项，用于决定输入目录中的字幕及其他非视频伴随文件是否复制到输出目录：

1. `不复制`：只处理识别到的视频文件，不复制任何外部字幕或其他非视频文件；
2. `仅复制字幕`：复制与输入目录扫描范围内识别到的字幕文件，例如 `.srt`、`.ass`、`.ssa`、`.vtt` 等，不复制其他非视频文件；
3. `复制其他文件`：复制扫描范围内的全部非视频文件，包含字幕、封面、NFO、章节、图片、文本等伴随文件。

第一版默认选择 `仅复制字幕`。三档必须为单选，不能使用两个可独立组合的开关。

复制时必须保持文件相对于输入根目录的原始目录结构，并映射到输出根目录；不得把伴随文件集中平铺到同一目录。视频文件仍按转码流程生成，伴随文件不得作为 FFmpeg 输入参与转码。

本地与 rclone 输入/输出组合均应支持该策略。对于远程存储，伴随文件复制应优先使用 rclone 的文件复制能力，不要求先下载到 FFmpeg 转码缓存；涉及远程写入时必须受现有单上传槽位约束，避免额外并发 rclone 写操作。

伴随文件目标已存在时，第一版采用与正式输出一致的保守策略：不得无提示覆盖；应记录冲突/失败原因，并允许 Retry。任务只有在所选范围内的视频处理和伴随文件复制均达到终态后才能进入最终完成状态。

该策略作为任务原始用户参数持久化，例如 `companion_file_policy = none | subtitles | all_non_video`，Retry 沿用原任务策略，不允许在 Retry 时静默改变。

#### 第二步：视频参数

提供常用参数选择，包括但不限于：

- 输出编码格式；
- 输出分辨率；
- 视频码率；
- 帧率策略；
- 音频处理方式；
- 输出封装格式。

第一版应优先提供常用选项，而不是直接暴露完整 FFmpeg 参数。

同时可以提供“高级参数”输入框，允许有经验的用户添加额外 FFmpeg 参数，但应用生成的必要硬件编解码参数应保持可控。

#### 第三步：编解码模式

至少提供：

1. CPU 解码 + CPU 编码；
2. CPU 解码 + GPU 编码；
3. GPU 解码 + GPU 编码。

GPU 模式使用 ffmpeg-rockchip 提供的 Rockchip MPP/RGA 等硬件能力。

GPU 解码 + GPU 编码时应尽可能保持硬件帧处理链路，减少不必要的：

`硬件帧 → CPU 内存 → 硬件帧`

转换。

涉及缩放、像素格式转换等操作时，应优先使用适合 Rockchip 硬件链路的方式实现，以尽量遵循零拷贝原则。

#### 第四步：确认任务

展示：

- 输入位置；
- 输出位置；
- 文件数量；
- 编码格式；
- 目标分辨率；
- 目标码率；
- 编解码模式；
- 伴随文件复制策略；
- 其他关键参数。

确认后创建任务并进入任务队列。

### 5. 任务管理及执行流程

任务列表一个任务显示一条记录。

至少展示：

- 任务名称或 ID；
- 当前状态；
- 创建时间；
- 输入目录；
- 输出目录；
- 总文件数；
- 已完成文件数；
- 当前转码文件；
- 当前上传文件（如果存在）；
- 整体进度；
- 当前转码阶段与上传阶段；
- 错误信息。

任务状态至少包括：

- 等待中；
- 运行中；
- 已完成；
- 部分失败；
- 失败；
- 已停止；
- 已中断。

其中“已中断”表示任务曾经处于运行阶段，但 FFPanel 进程或容器异常退出，当前已经没有可信的活动子进程。该状态必须可 Retry。

单个远程视频文件的内部处理流程建议为：

`等待 → 下载 → 预检 → 转码 → 待上传 → 上传 → 完成`

其中 `待上传 (upload_queued)` 是一个持久化安全检查点：FFmpeg 已成功结束、本地转码产物已完成文件大小检查，但尚未完成远程提交。进入该状态后立即释放唯一 FFmpeg 转码槽位，使下一视频可以进入下载/预检/转码链路；上一视频的上传由独立的单上传槽位执行，因此允许出现“视频 A 上传 + 视频 B 转码”的流水线并行。

本地输出不经过上传队列，转码成功并完成原子提交后即可标记完成。

支持：

**停止任务**

停止该任务当前占用的 FFmpeg/rclone 子进程，并阻止该任务继续领取新的转码或上传工作。由于上传槽位与转码槽位相互独立，同一时刻可能存在两个活动文件；Stop 必须分别终止属于该任务的活动转码和活动上传，但不得误杀其他任务已经占用的另一槽位。

**删除任务**

删除任务记录，并清理与该任务相关的临时文件。

对于已经成功生成的目标视频，删除任务默认不删除输出文件。

某一个视频处理失败时，应记录具体错误。任务可以根据策略继续处理后续文件，最终任务状态显示为“部分失败”。

启用伴随文件复制时，后端应在创建任务的目录扫描结果中同时记录待复制伴随文件清单及相对路径。伴随文件复制失败需要记录具体文件与错误原因；只要存在未解决的伴随文件复制失败，任务不得显示为纯 `completed`，应进入可解释的 `partial_failed` 或 `failed` 状态。

**Retry 任务**

Retry 不创建重复的顶层任务记录，而是在原任务上增加一次 retry attempt：

- 已成功文件保持成功并跳过；
- 失败、已中断、尚未开始的文件根据最近一次安全检查点进入对应队列；
- 转码阶段中断的 `.part` 必须清理，并从转码安全检查点重新执行；
- 已进入 `upload_queued`，或上传阶段中断但本地完整转码产物大小匹配的文件，Retry 只重新进入上传队列，不重复 FFmpeg 转码；
- 本地转码产物缺失、大小不匹配或未记录产物大小时，才回退到重新 ffprobe、参数决策和转码；
- 每次 Retry 需要记录 `attempt`、触发时间和上一次错误原因；
- 任务原始“用户参数”保持不变；只有需要重新转码的文件才再次运行 ffprobe 与参数决策器，以适应源文件或硬件能力发生变化的情况。

第一版不提供真正的“暂停后从 FFmpeg 中间帧继续编码”。所谓 Retry 是从文件级安全检查点重新处理，而不是续接一个已经退出的 FFmpeg 进程。

### 6. HTTP Basic Auth

支持通过 Docker 环境变量启用 HTTP Basic Auth，用于局域网中的基础访问控制。

例如通过环境变量配置：

- 是否启用认证；
- 用户名；
- 密码。

未配置认证相关环境变量时默认关闭认证。

Basic Auth 应保护 WebUI 和后端 API，避免只保护前端页面而可以直接访问 API。

认证密码不得写入任务数据库或日志。

### 7. 智能分辨率、码率与参数决策原则

每个视频正式转码之前必须执行 ffprobe 预检，并统一交给“转码参数决策器”生成最终实际参数。业务代码不得在多个 Worker 分支中各自拼接一套 FFmpeg 参数，详细规则见第 11 节。

原则为：

**不因为转码主动提高源视频的分辨率。**

例如：

源视频：1280×720  
用户目标：1920×1080

实际输出仍使用：

1280×720

如果：

源视频：3840×2160  
用户目标：1920×1080

则输出：

1920×1080

码率采用类似逻辑：

如果源视频码率低于用户设置的目标码率，则使用源视频码率作为实际目标参考值，避免将低码率视频重新编码成更高码率而无意义增加文件体积。

如果源视频码率高于目标码率，则使用用户设置的目标码率。

除分辨率与码率外，最终参数还必须同时考虑：

- ffprobe 获得的源视频/音频/字幕流参数、旋转信息、时长和像素格式；
- 用户选择的编码格式、封装格式、硬件模式、帧率、音频/字幕策略及高级参数；
- MP4、MKV 等目标容器对视频、音频、字幕 codec/tag 的兼容性；
- 应用启动时探测到的 RK3588 MPP/RGA/编码器/解码器能力；
- FFPanel 为保证临时输出、结构化进度和硬件链路而强制注入的系统参数。

必须区分并持久化：

- `source_params`：ffprobe 获取并标准化后的源参数；
- `requested_params`：用户在创建任务时提交的原始目标参数；
- `effective_params`：决策器最终采用的实际参数；
- `decision_log`：每一项自动调整的原因，例如“不放大分辨率”“源码率低于用户上限”“MP4 不兼容当前字幕编码”“GPU 模式能力检测失败”等。

前端展示“用户目标”时不得把它误写为该文件的最终实际参数；实际参数只有在该文件完成 ffprobe 与参数决策后才确定。

### 8. ffmpeg-rockchip 构建及硬件加速

Docker 镜像构建阶段从：

`https://github.com/nyanmisaka/ffmpeg-rockchip`

获取源码并完成编译。

最终运行镜像直接包含编译好的 FFmpeg/ffprobe。

应用不得依赖宿主机上的：

`ffmpeg`

或：

`ffprobe`

版本。

构建时应包含 RK3588 所需的硬件编解码支持。

应用启动时可以执行一次能力检测，例如检查：

- ffmpeg 是否存在；
- ffprobe 是否存在；
- Rockchip 硬件设备是否可访问；
- MPP 编解码能力是否正常。

如果硬件加速不可用，应在 WebUI 明确提示。

CPU 编解码模式仍应可以正常使用，不应因为 GPU 不可用导致整个应用无法启动。

### 9. 远程文件预检、缓存及原脚本功能参考

远程目录创建任务时，只通过 rclone 获取文件列表、文件大小、修改时间等基础信息，不在创建任务阶段对所有远程视频批量执行 ffprobe，以避免创建任务长时间阻塞。

Worker 真正处理某个远程文件时：

1. 使用 rclone 将视频下载到 `/cache` 下对应任务的临时目录；
2. 下载成功后使用 ffprobe 对本地缓存文件进行预检；
3. 获取视频编码、分辨率、码率、帧率、时长、音视频流等必要信息；
4. 将标准化后的 ffprobe 结果、任务用户参数、目标容器和当前硬件能力交给统一参数决策器；
5. 持久化本文件的 `source_params / requested_params / effective_params / decision_log`；
6. 使用决策器生成的参数调用 ffmpeg-rockchip 执行转码，并启用结构化 `-progress` 输出；
7. 转码输出先写入临时文件；
8. 转码成功后，通过 rclone 上传到目标 remote 的临时目标；
9. 上传成功后再完成最终文件提交/重命名，并更新持久化状态；
10. 根据配置清理输入缓存和输出临时文件。

任务被停止、FFmpeg 异常退出或上传失败时，不应将未完成文件视为成功输出。

缓存目录需要按任务进行隔离，例如：

`/cache/tasks/<task-id>/`

并在任务完成或删除后清理不再需要的临时文件。

### 10. 任务持久化与异常恢复机制

#### 10.1 持久化边界

任务执行状态必须以持久化数据库为准，不能只保存在内存、Pinia、日志或 `/cache` 目录中。第一版建议使用 SQLite，数据库文件位于 `/config/ffpanel.db`，并启用 schema version/migration 机制。

建议至少维护两个核心实体：

**Task**

- `id`、`name`；
- `status`：`queued / running / completed / partial_failed / failed / stopped / interrupted`；
- `created_at / started_at / finished_at / updated_at`；
- 输入、输出位置及存储类型；
- `requested_params_json`：用户创建任务时的原始参数，包含 `companion_file_policy`；
- 文件总数、成功数、失败数、跳过数，并可单独统计伴随文件待复制/成功/失败数量；
- 当前转码文件 ID（可空）；
- 当前上传文件 ID（可空）；
- 转码队列位置/租约信息与上传队列位置/租约信息；
- `retry_count`；
- `last_error`、`interrupted_reason`。

**TaskFile**

- `id / task_id / relative_path`；
- `status` 与 `stage`：`pending / downloading / probing / transcoding / upload_queued / uploading / completed / failed / interrupted / skipped`；
- `attempt`；
- 源文件大小、修改时间等 fingerprint；
- `source_params_json`；
- `effective_params_json`；
- `decision_log_json`；
- 当前 FFmpeg 临时输出路径、已完成待上传的本地产物路径、最终输出路径；
- 本地产物大小与 `transcode_completed_at`；产物复用只比较文件大小；
- `last_error / last_exit_code`；
- 最近一次结构化进度快照；
- `started_at / finished_at / updated_at`。

所有关键状态切换必须先后端落库，再向前端广播状态事件。数据库更新失败时不得仅靠内存把任务继续推进到下一阶段。

#### 10.2 Docker/进程启动恢复

FFPanel 每次启动时执行一次 recovery scan：

1. 读取数据库中所有非终态任务；
2. `queued` 任务保持排队，可由本次进程继续调度；
3. 上一次记录为 `running` 的任务统一标记为 `interrupted`；由于采用双槽位流水线，启动时最多可能发现一个处于 `downloading / probing / transcoding` 的转码链路活动文件，以及一个处于 `uploading` 的上传活动文件；
4. 对上述真正处于活动子进程阶段的文件标记为 `interrupted`，写入 `interrupted_reason = process_restart` 或 `unclean_shutdown`；
5. 已经 `completed` 的文件绝不回退；已经持久化为 `upload_queued` 的文件也不回退到转码阶段，其本地产物大小检查通过后继续作为待上传安全检查点；
6. 清理已知不完整的 FFmpeg `.part` 输出；下载缓存仅在 fingerprint 校验通过时允许复用；对上传中断文件保留已经完整生成的本地转码产物；
7. 将恢复结果通过 API/SSE 暴露给前端，显示“检测到上次运行中断，可 Retry”，并分别指出中断的是转码链路还是上传链路。

收到 Docker `SIGTERM` 时，应优先终止当前 FFmpeg 子进程以及当前 rclone 上传子进程（如存在），分别把对应活动文件安全写为 `interrupted` 后退出；`upload_queued` 文件保持安全检查点不变。对于 `SIGKILL`、断电等无法执行清理的情况，由下一次启动 recovery scan 兜底。

#### 10.3 文件级安全检查点与幂等性

Retry 以“文件”为最小恢复单位，不尝试续接 FFmpeg 编码进度：

- `completed`：直接跳过；
- `pending / failed / interrupted`：根据最近一次可验证安全检查点恢复；
- 下载完成且缓存 fingerprint 与任务记录一致：可复用输入缓存并从 ffprobe 开始；
- 转码中的 `.part`：默认删除并从转码开始重做；
- `upload_queued`：本地完整转码产物大小检查通过后直接重新进入上传队列，不重复转码；
- `uploading` 中断：远程临时目标视为未完成，重试前清理或覆盖；本地完整转码产物大小检查通过时仅重试上传；
- 本地完整转码产物缺失、大小不匹配或未记录大小：回退到重新转码；
- 最终输出提交前应先持久化预期输出大小，恢复时只按文件大小确认产物。

本地输出使用“临时文件 → 原子 rename/replace → 状态落库”的方式提交。远程输出建议“上传临时远程名 → rclone move/moveto 为最终名 → 状态落库”。如果进程恰好在最终 rename 后、数据库更新前退出，恢复逻辑应先用已记录的输出大小检查最终目标；能够确认成功则补记 `completed`，无法确认时标记冲突并要求 Retry/人工处理，不能直接覆盖已有正式输出。

### 11. 统一转码参数决策器

项目内只能有一个“最终 FFmpeg 参数生成入口”。Worker 负责收集输入，参数决策器负责生成不可变的 `effective_params` 和最终 argv，执行器不得在调用 FFmpeg 前再次偷偷改参数。

#### 11.1 输入

决策器输入固定分为四组：

1. **Source Probe**：ffprobe JSON 标准化结果；
2. **Requested Params**：用户任务参数；
3. **Container Constraints**：目标 MP4/MKV 等容器兼容规则；
4. **Runtime Capabilities**：启动时检测到的 ffmpeg-rockchip、MPP、RGA、可用 encoder/decoder/filter 能力。

#### 11.2 决策顺序

建议固定为以下顺序，避免参数相互覆盖：

1. 标准化源参数：处理 rotation、SAR/DAR、实际显示宽高、主视频流、音频/字幕流；
2. 校验用户参数：范围、组合合法性、高级参数冲突；
3. 决定解码器与编码器实现；
4. 决定是否需要缩放、像素格式转换，以及是否可保持 MPP/RGA 硬件帧链路；
5. 应用“不主动升分辨率”和 Smart Bitrate Cap；
6. 根据目标容器决定音频/字幕 copy、转码或拒绝；
7. 合并允许的高级参数；
8. 注入 FFPanel 强制参数：临时输出、结构化 progress、必要的 map/muxer/hardware 初始化参数；
9. 输出最终 argv 和逐项 `decision_log`。

第一版对高级参数采用“受控合并”：用户高级参数不得覆盖输入路径、输出路径、`-progress`、硬件初始化、最终视频 encoder、muxer 等系统关键参数；检测到冲突时在创建任务或文件预检阶段明确报错，而不是依赖参数顺序产生隐式覆盖。

#### 11.3 能力不足时的原则

任务参数提供默认开启的 `autoFallback` 显式退回策略。开启时，每个文件从用户选择的档位开始逐级尝试：`mpp_mpp → cpu_mpp → cpu_cpu`，或从 `cpu_mpp → cpu_cpu`；选择纯 CPU 时不再退回。关闭时只尝试用户指定的模式，能力不足或转码失败即明确报错。

自动退回只覆盖能力/参数决策、FFmpeg 执行及输出有效性检查。源文件下载与探测、目标冲突、产物提交、上传、用户停止和任务取消均不得触发换档。每次换档必须清理失败的临时输出、重置进度，并将失败模式、原因、下一模式和最终实际参数写入文件决策记录与诊断日志；原始 `requested_params` 始终保持不变。

#### 11.4 可观测性

每个文件应能从 API 查询：

- 源参数；
- 用户参数；
- 实际参数；
- 决策原因列表；
- 实际 FFmpeg argv（敏感路径可按日志策略脱敏）；
- ffmpeg 版本与硬件能力快照标识。

这些信息用于前端“参数决策”面板、问题复现和 Retry 对比。

### 12. 单进程、单转码 + 单上传流水线调度机制

第一版明确限制为**单 FFPanel 应用进程 + 1 个 FFmpeg 转码槽位 + 1 个上传槽位**。核心原则是 **FFmpeg 转码严格单并发，但允许“上一文件上传 + 下一文件转码”并行**；不实现多个 FFmpeg 并发转码、多 Worker 消费或复杂资源配额。

#### 12.1 进程与槽位约束

- Docker 运行时只启动 1 个 FFPanel application process；前端使用 Vite 构建后的静态资源，由同一应用进程提供，不额外启动 Node dev server/Nginx Worker；不得配置多个 Web worker 共同消费任务；
- 建议对 `/config/ffpanel.lock` 使用进程级独占锁，第二个 FFPanel 实例检测到锁占用后直接退出并给出明确日志；
- Web API、转码调度器、上传调度器和状态恢复逻辑位于同一应用进程；
- ffmpeg、ffprobe、rclone 仍作为受控子进程启动，不计为第二个 FFPanel Worker；
- 全项目任意时刻 `Transcoding` 文件数必须 `<= 1`，绝不允许同时存在两个 FFmpeg 转码进程；
- 全项目任意时刻 `Uploading` 文件数必须 `<= 1`，避免多个远程上传同时争抢网络、磁盘与缓存 I/O；
- 转码槽位与上传槽位相互独立，因此允许同时存在 1 个 `Transcoding` 文件和 1 个 `Uploading` 文件，它们可以属于同一任务，也可以在任务边界处属于不同任务。

#### 12.2 两阶段流水线

远程输出文件采用两阶段流水线：

1. **转码链路**：`pending → downloading → probing → transcoding`；
2. FFmpeg 正常退出并完成本地产物文件大小检查后，持久化为 `upload_queued`；
3. 一旦 `upload_queued` 落库成功，立即释放 FFmpeg 转码槽位，允许下一文件开始下载/预检/转码；
4. **上传链路**：独立上传调度器领取最早的 `upload_queued` 文件，执行 `uploading → completed`；
5. 因此典型时序为：`视频 A uploading || 视频 B transcoding`；
6. 对本地输出，没有上传阶段，转码成功并完成原子提交后直接 `completed`。

对于远程输入，下一文件的下载/预检属于转码链路准备阶段，也可以与上一文件上传重叠；但转码链路本身仍一次只推进一个文件，不额外引入多个下载/预检 Worker。

#### 12.3 FIFO 与有界缓冲

- 转码链路采用 FIFO：按任务创建顺序选择任务，再按任务内文件顺序领取下一待转码文件；
- 上传链路也采用 FIFO：按进入 `upload_queued` 的时间顺序上传；
- 第一版不提供优先级、抢占或用户可配置并发度；
- 为避免远程上传明显慢于转码时无限堆积本地产物，第一版采用**单缓冲背压**：除当前 `uploading` 文件外，最多允许再保留 1 个 `upload_queued` 文件；
- 当已经存在 `1 uploading + 1 upload_queued` 时，转码调度器暂不领取新的远程输出文件；待上传队列腾出位置后再继续。这样仍可稳定实现“A 上传 + B 转码”，同时限制 `/cache` 占用增长；
- 如果目标是本地输出，则不受上传缓冲限制。

#### 12.4 Stop、完成条件与任务边界

- 一个任务只要仍存在 `transcoding / upload_queued / uploading` 等未完成文件，就不能标记为 `completed`；
- 某任务最后一个文件完成转码但仍在上传时，该任务保持 `running`；此时转码槽位可以继续处理后续任务的文件；
- 因此同一时刻可以出现“任务 A 仅剩上传、任务 B 正在转码”，前端必须能够同时展示两条活动链路；
- Stop 某任务时，只终止属于该任务的活动 FFmpeg/rclone 子进程，并撤销该任务尚未领取的新工作；如果另一槽位正在处理其他任务，不得受影响；
- API 服务必须使用异步/非阻塞方式同时等待 FFmpeg 与 rclone 子进程输出，避免转码或上传期间 WebUI 无法查询状态或发送 Stop。

该约束的目标是在不引入并发转码复杂度的前提下隐藏远程上传等待时间，提高 RK3588 硬件转码槽位利用率。未来如果继续增加上传并发、预下载或多个 FFmpeg 槽位，必须再引入显式资源租约、缓存水位与 I/O 限流机制。

### 13. 结构化 FFmpeg 进度机制

转码进度不得再以解析人类可读 stderr 文本作为主方案。执行 FFmpeg 时统一启用机器可读进度：

```bash
ffmpeg -nostdin -progress pipe:1 -nostats -stats_period 0.5 ... <output.part>
```

其中：

- **stdout**：仅解析 `-progress` 产生的 `key=value` 数据；
- **stderr**：保留 FFmpeg 日志、warning、error，用于诊断，不参与核心进度计算；
- 每遇到 `progress=continue` 形成一个完整进度快照；`progress=end` 表示 FFmpeg 正常走到进度流末尾，但最终成功仍需同时检查进程 exit code、输出文件存在且大小大于零。

建议解析并标准化以下字段：

- `frame`；
- `fps`；
- `bitrate`；
- `total_size`；
- `out_time_us`（首选）；必要时兼容 `out_time_ms/out_time`，但解析器必须统一换算为内部毫秒值；部分 FFmpeg 版本中的原始 `out_time_ms` 名称与实际时间单位并不直观，不能直接按字段名假设单位；
- `speed`；
- `dup_frames / drop_frames`（若提供）；
- `progress`。

进度百分比使用 `out_time / ffprobe.duration` 计算，并限制在 `0~100%`；ETA 在 `speed > 0` 且时长可信时计算。对于 duration 缺失或不可信的媒体，前端显示帧数、速度和已处理时间，但不伪造百分比/ETA。

为避免 SQLite 高频写入，500ms 左右的实时快照主要通过 SSE 推送；数据库只需要节流保存最近快照（例如每 2~5 秒一次）以及阶段变化、停止、失败、完成等关键节点。WebUI 断线重连时先通过 REST 获取数据库中的最新快照，再继续接收 SSE 增量事件。

建议统一后端进度对象：

```json
{
  "task_id": "...",
  "file_id": "...",
  "stage": "transcoding",
  "frame": 12345,
  "fps": 118.4,
  "bitrate_kbps": 1850.2,
  "out_time_ms": 93210,
  "total_size_bytes": 218734592,
  "speed": 3.72,
  "percent": 42.1,
  "eta_seconds": 128,
  "progress": "continue"
}
```

前端只消费该结构化对象，不自行解析 FFmpeg 原始日志。
