# 硬件后端接口

## 调用路径

```text
detect_capabilities → FFmpeg 清单、hwaccels、设备节点 → registry.probe
                   → 新 GPU 运行时探测 → CapabilitySnapshot

decide_parameters → 公共尺寸/码率策略 → backend.plan_video
                  → 公共音轨/字幕校验 → effective/reasons

build_ffmpeg_argv → restore_video_plan → backend.build_video_args
                 → 公共输入输出、流映射、音频字幕和容器参数

scheduler → registry.mode_chain / registry.label → 执行、取消、记录尝试与回退
```

`media.py` 保留原有函数及 `CapabilitySnapshot`、`MediaError` 导入路径。
现有 CPU/MPP 的参数决策、argv 顺序、API 方案标识及回退语义保持兼容。

## 后端契约

`hardware/types.py` 定义 `HardwareBackend` Protocol 与 dataclass：

- `id` 与 `device_paths` 描述后端及通用检测节点。
- `probe(inventory)` 同步解释编码器、解码器、滤镜、hwaccels 与节点清单。
- `profiles()` 返回方案标识、名称、所属后端、解码方式及下一回退方案。
- `plan_video(request, profile, capabilities)` 校验并返回确定性的视频计划；不自行回退。
- `build_video_args(plan)` 返回输入前、输入后的独立 argv 元素，不生成 shell 字符串。

`VideoRequest` 包含源编码、源像素格式、目标编码及公共 `VideoSettings`。
`VideoPlan` 保存方案、编码器、尺寸/旋转/SAR/码率/帧率，以及滤镜、设备和输出像素格式。
新增 GPU 的 `effective.hardwareDevice`、`effective.pixelFormat` 与 `scaleFilter` 持久化，
命令还原不重新探测，也不读取可能已经改变的设备环境变量。CPU/MPP 不增加这些字段。

后端不处理文件路径、数据库、任务、进程、音频字幕、上传、取消或缓存。
`hardware/gpu.py` 共享 GPU 规划与命令机制，注册 NVIDIA、QSV、VAAPI 三个独立后端。
NVIDIA 的软件解码方案由 NVENC 上传系统内存帧；Intel 软件解码方案显式上传硬件帧。
新增硬解方案遇到旋转或不支持的像素格式时抛出能力错误，由调度器执行下一方案。

## 能力检测与 API

`hardware/detection.py` 是 GPU 进程和设备检查的集中边界。先检查设备存在性、Intel
sysfs 厂商与读写权限，再按部署指定的设备执行初始化、H.264/HEVC 编码、硬解和缩放探测。
单项超时或取消会杀死并回收子进程；错误只影响对应后端/能力。短素材在临时目录生成并清理。
探测中下载帧到空输出用于检查解码结果，不会插入生产硬件转码计划。

探测每次启动执行一次，状态广播复用结果。`features` 的 `encode_h264`、`encode_hevc`、
`decode_h264`、`decode_hevc`、`decode`、`scale` 表示运行时结果；`compiled` 只表示编译支持。
对其他源编码还要校验 FFmpeg 解码器清单及实际执行结果，不能从基础样本推断所有格式均可用。
MPP/RGA 保留原有编译清单与节点的联合检测规则。

Snapshot 与 `system.status` SSE 共用新增字段：

- `hardwareBackends[]`：`id`、`label`、`group`、`detected`、`status`、`device`、
  `features`、`errors`、`encoders`、`decoders`、`filters`。
- `hardwareProfiles[]`：`id`、`label`、`backendId`、`decodeMode`、`fallback`、
  `detected`、`available`、`codecs`、`reason`。`codecs` 是可用的目标编码列表；
  具体输入是否可硬解，在逐文件 ffprobe 后判断。
- `recommendedHardwareMode`：针对默认 HEVC 目标的建议。前端切换编码时使用同一优先级
  重新计算：NVIDIA、QSV、VAAPI、MPP、CPU，各后端先硬解后软解；手动选择后不覆盖。

状态值为 `detecting`、`ready`、`partial`、`unavailable`。
旧的 `mppAvailable`、`rgaAvailable`、工具清单和设备字段保留；清单现在包含新增后端编译能力。
`compat.py` 是旧快照适配边界，旧 MPP/RGA 布尔值仍为权威值。旧快照没有 GPU 运行时结果，
即使列出 NVENC 编码器也不能推断 GPU 可用。mock 不执行任何真实设备检查或子进程。

## 注册、回退与持久化

注册表显式注册 CPU、Rockchip、NVIDIA、QSV、VAAPI，拒绝重复后端/方案、
所属后端不符、缺失回退目标及环。不存在动态插件发现。

| 后端 | 完整回退链 |
| --- | --- |
| Rockchip | `mpp_mpp → cpu_mpp → cpu_cpu` |
| NVIDIA | `nvdec_nvenc → cpu_nvenc → cpu_cpu` |
| QSV | `qsv_qsv → cpu_qsv → vaapi_vaapi → cpu_vaapi → cpu_cpu` |
| VAAPI | `vaapi_vaapi → cpu_vaapi → cpu_cpu` |

关闭自动回退只执行请求方案。从中间方案开始仅执行后续链路。
调度器保留规划失败与 FFmpeg 执行失败记录，每次失败后清理输出、重置进度并尝试下一方案，
不提前剔除不可用方案。取消不触发下一档，Retry 保留原请求。API 默认模式仍为 `mpp_mpp`，
以兼容已有客户端；新版前端会明确提交动态选择的模式。

Alembic `0004_hardware_capabilities` 为 `runtime_capabilities` 增加 `hardware_json`，
保存完整的新能力响应。旧行回填空对象，序列化时用旧字段补兼容描述。文件仍关联启动时的
能力快照；任务与 `effective` 继续使用现有 JSON 持久化机制。

## 验证

运行 `pytest`、`ruff check .`、`mypy ffpanel`，导出 OpenAPI 后执行前端 `npm run check`。
CPU/MPP 的完整 argv 基线保留；新增 GPU 参数矩阵、探测故障/超时/取消、厂商权限、
API/迁移、调度回退/取消/Retry 和前端动态选择测试无需 GPU。

镜像与实机验证的边界、驱动要求及脚本入口见 [GPU 部署与验证](GPU部署与验证.md)。
